zombie websockets

How to detect and recover from half-open TCP connections on real-time gateways when no FIN or RST frames are transmitted.

2026-10-25 · 6 min read · distributed systems & tcp

In distributed real-time systems—such as Discord bot runtimes, financial ticker feeds, and IoT telemetry pipelines—the most deceptive failure mode is not a crash or a broken connection. It is the Zombie Connection: a socket that is completely dead, yet the operating system believes is in state ESTABLISHED.

When an intermediate NAT router drops state, an ISP drops routing tables, or a server experiences sudden power loss, no TCP FIN or RST packet is ever sent. From the perspective of Node.js:

  • No 'error' event fires.
  • No 'close' event fires.
  • The WebSocket readyState remains 1 (OPEN).
  • Zero inbound messages arrive, leaving your application stranded in silence.

Why OS TCP Keepalives Are Ineffective

Developers often assume the operating system’s built-in TCP keepalive will resolve this issue. In practice, default Linux kernel settings render OS keepalives useless for real-time services: 

# Default Linux kernel TCP keepalive settings
cat /proc/sys/net/ipv4/tcp_keepalive_time   # 7200 seconds (2 hours!)
cat /proc/sys/net/ipv4/tcp_keepalive_intvl  # 75 seconds
cat /proc/sys/net/ipv4/tcp_keepalive_probes # 9 probes

By default, your process will wait over 2 hours before the OS detects a dead socket. Even when tuned via socket.setKeepAlive(true, 15000), transport-level TCP probes only verify that the remote kernel is reachable; they cannot verify whether the remote application process or gateway event loop is responsive.

The Heartbeat State Machine Pattern

In the June runtime architecture, connection liveness is guaranteed at the application protocol layer using a hardened Heartbeat State Machine: 

// Finite State Machine transitions for Gateway Heartbeat
// [CONNECTED] --(Send Heartbeat)--> [AWAITING_ACK] --(Receive ACK)--> [HEALTHY]
//                                         |
//                                (Timeout / No ACK)
//                                         v
//                                 [FORCE_DESTROY] --> [RESUME]

1. Initial Handshake & Jitter Calculation

Upon establishing the raw WebSocket handshake, Discord’s gateway immediately sends Opcode 10 (HELLO) containing the required heartbeat_interval (typically 41,250 ms).

If thousands of clustered bot shards reboot simultaneously after a data center blip, transmitting heartbeats at exact intervals would cause a synchronized thundering herd. We introduce a uniform random jitter on the first tick: 

// Randomize the initial heartbeat timing
const initialDelay = heartbeatInterval * Math.random();
setTimeout(() => {
  sendHeartbeat();
  // Subsequent heartbeats run on fixed interval
  heartbeatTimer = setInterval(sendHeartbeat, heartbeatInterval);
}, initialDelay);

2. Detecting the Zombie State (ACK Deadlines)

The core invariant of the state machine is that every outbound Opcode 1 (HEARTBEAT) must be answered by an inbound Opcode 11 (HEARTBEAT_ACK) before the next interval elapses.

If a new interval arrives and the previous heartbeat was never acknowledged, the socket is dead: 

let hasAcked = true;
let lastHeartbeatSentAt = 0;

function sendHeartbeat() {
  if (!hasAcked) {
    // ZOMBIE DETECTED: Remote peer failed to acknowledge prior heartbeat
    console.warn("[gateway] Heartbeat ACK missing. Forcing hard socket destruction...");
    
    // CRITICAL: Call socket.destroy(), NOT ws.close()
    // ws.close() attempts a 2-way TCP close handshake that will hang indefinitely!
    ws.terminate(); 
    return;
  }

  hasAcked = false;
  lastHeartbeatSentAt = Date.now();
  
  // Transmit Opcode 1 with the last acknowledged sequence number
  ws.send(JSON.stringify({
    op: 1,
    d: lastSequenceNumber // null or integer (e.g. 14205)
  }));
}

function handleMessage(raw) {
  const payload = JSON.parse(raw);
  
  // Opcode 11: Heartbeat Acknowledgment
  if (payload.op === 11) {
    hasAcked = true;
    latencyMs = Date.now() - lastHeartbeatSentAt;
    return;
  }
  
  // Update rolling sequence number for reliable replay
  if (payload.s !== null) {
    lastSequenceNumber = payload.s;
  }
}
Why ws.terminate() instead of ws.close()? ws.close() initiates the standard WebSocket closing handshake by sending a close frame (0x8) and waiting for a matching close frame from the server. On a dead TCP connection, the response frame will never arrive. ws.terminate() or socket.destroy() instantly drops the kernel file descriptor, bypassing the network stack and triggering immediate reconnect routines.

Fast Session Resumption (Opcode 6)

When a connection is terminated, a naive client initiates a brand new connection using Opcode 2 (IDENTIFY). This causes massive overhead: Discord must re-serialize and transmit thousands of guild state objects, role permissions, and channel structures.

Instead, we preserve the session_id and lastSequenceNumber across socket resets, and issue Opcode 6 (RESUME): 

function onReconnected() {
  if (sessionId && lastSequenceNumber !== null) {
    console.log(`[gateway] Attempting session resumption: ${sessionId} at seq ${lastSequenceNumber}`);
    ws.send(JSON.stringify({
      op: 6,
      d: {
        token: process.env.DISCORD_TOKEN,
        session_id: sessionId,
        seq: lastSequenceNumber
      }
    }));
  } else {
    sendFullIdentify();
  }
}

If the gateway successfully verifies the session, it responds with Opcode 0 (RESUMED) and replays only the exact event packets that were missed during the disconnect window. Downtime is measured in milliseconds, without any user-visible interruption.

Multi-Shard Boot Staggering

Discord limits clients to 1 identify attempt every 5 seconds per gateway rate-limit bucket. When scaling across multiple worker processes:

  • Shards must never connect concurrently on application boot.
  • Shard spawns are staggered using a 5,500ms safety delay (5,000ms rate-limit + 500ms network jitter cushion).
  • This ensures 100% compliance with Discord API rate limits, avoiding account-level IP bans and 4004 (Authentication Failed) disconnections.

Summary

Building high-availability real-time applications requires treating TCP connections as inherently fragile:

  • Never rely on the OS or basic socket events to discover disconnects.
  • Enforce application-level heartbeats with strict deadline enforcement.
  • Use hard socket destruction (destroy()) to guarantee instant cleanups.
  • Leverage protocol sequence numbers to achieve seamless session resumption.
